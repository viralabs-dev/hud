# HUD runner migration slice

This isolated crate implements configured command execution for AT-071. Python reference: `hud/runner.py`, `hud/config.py::resolve_executable/build_command`, `hud/plataforma.py::kill_tree`, and `hud/text.py::clean`. It is a worker adapter, not an integration with active user configuration.

`ConfiguredCommand::new` validates fixed argv, an existing working directory, 0 < timeout <= 600 seconds and 1 <= max_lines <= 5000. Executables resolve only through the fixed system PATH (or an explicitly configured absolute path), with forbidden launchers denied before and after canonicalization. The executable and immediate resolved parent must be root/current-UID owned and cannot have group/world write bits; this is deliberately stricter than Python's private-group exception. Runtime revalidation repeats these checks. No shell interpolation occurs. Arguments remain literal. Programs configured by the owner can themselves have side effects; this is not an OS sandbox.

The environment is cleared and replaced by the eleven documented safe variables. There is a shared 256 KiB raw-output budget for stdout and stderr. Both pipes are drained nonblocking with bounded per-turn work, so a continuous writer cannot starve timeout/cancellation. UTF-8 is decoded with replacement, terminal escape payloads/control/bidi characters are removed, and each stream has the configured line ceiling. Stdout/stderr are separate; relative inter-stream ordering and the Python merged-stream line ceiling are not preserved yet.

The child starts in its own POSIX process group. Timeout/cancellation force-kill that group; `waitid(... NOWAIT)` keeps the leader unreaped until group signalling completes, avoiding a PID reuse window. A 300 ms post-kill drain deadline prevents a descendant holding pipes open from blocking the worker. Escaped sessions/process groups are outside this containment guarantee. The child is reaped on cleanup, including errors. Test fixtures prove a descendant becomes absent or non-runnable zombie after group cancellation; zombies adopted by the container are not claimed reaped by HUD.

`Runner::start` reserves a key and returns `None` while that key runs, then releases it after success or failure. `Running::try_result` is nonblocking for the TUI. Explicit cancellation or dropping the handle cancels the worker. `requiring_confirmation` commands fail closed through ordinary `run/start`; UI approval must explicitly invoke `run_with_confirmation/start_confirmed` with `Confirmation::Approved`. The crate does not manufacture user approval or show a confirmation UI.

Windows returns `Unsupported` before executable resolution/spawn. No Job Objects adapter is implemented. Only Linux was compiled/executed; macOS source is unvalidated. There is no global environment/configuration change or active agent execution.

Validation on Linux: `cargo test --offline`, `cargo clippy --offline --all-targets -- -D warnings`, `cargo fmt --check`; 13 integration tests. `src/bin/runner-fixture.rs` is solely a harmless contract fixture and must not be included in user-facing distribution. Integrate `src/lib.rs`, fixture and tests into the root-owned workspace; root owns workspace manifest/lock/docs/Vault changes. Cargo.lock here is only the staged crate build lock.

Remaining acceptance/integration: wire owner-configured commands and confirmation UI; demonstrate cancellation from the real TUI; decide merged-stream parity; Windows process-tree adapter and native platform testing; same-UID executable substitution/ancestor path races require a future descriptor-bound exec design if stronger guarantees are required.
